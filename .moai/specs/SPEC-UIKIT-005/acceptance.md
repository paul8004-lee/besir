# SPEC-UIKIT-005 — acceptance.md

계획 SPEC이므로 전 AC를 ⬜(미확인)로 시작한다.

**이 문서의 조직 원리는 "누가 볼 수 있는가"다.** 이 카드가 고치는 값은 **좌표**이고, 좌표는
화면 어디에도 찍히지 않는다. 그래서 각 AC는 자기 판정이 **run/sync가 돌리는 명령**으로 닫히는지
(`grep` · 빌드 · 드라이버 · `git diff`), 아니면 **시뮬레이터나 실기기 앞의 사람만** 볼 수 있는지를
먼저 밝힌다. 둘이 섞인 AC는 절마다 갈라 적는다.

**기계가 볼 수 있는 것은 "열쇠가 바뀌었다"까지다.** "고른 좌표가 실제로 실렸다"는 명령으로 잴 수
없다 — 같은 상호의 다른 지점을 **두 줄에 직접 골라야** 드러나고, 그 조작은 사람만 할 수 있다.
드라이버가 `AIAssistant.swift`를 컴파일 대상에 넣는다는 사실(`CLAUDE.md` § 빌드 · 배포)은
**인자 경로**를 덮을 뿐 이 조작을 덮지 않는다. 205/205 초록 다음 날 실기기 결함 7건이 나온 이력이
이 프로젝트에 있다(2026-09-15).

**AC-009가 대체 불가능한 증거다.** 나머지 여덟 중 어느 것도 AC-009를 대신하지 못하고, AC-009가
🟡를 ✅로 올리는 유일한 경로다.

## AC-001 — `AddEventView`의 좌표 사전이 줄 신원으로 걸리고 읽기가 fail-closed다 ⬜

**관측자: 기계.** 전 절이 명령으로 닫힌다.

- **Given** `@State private var confirmedPlaces: [String: Place] = [:]`(`AddEventView.swift:19`)가
  이름을 열쇠로 쓰고, 읽기가 `field(key)?.chosen.flatMap { confirmedPlaces[$0] }`(`:511-512`)라
  `chosen`이 있으면 이름으로 조회하며
- **When** 열쇠가 `[UUID: Place]`가 되고 읽기가 t3와 같은 fail-closed 형태로 바뀌면
- **Then** 넷이 동시에 성립한다:
  1. `grep -c "\[UUID: Place\]" Shared/AddEventView.swift`가 **1**이고
     `grep -c "confirmedPlaces: \[String: Place\]" Shared/AddEventView.swift`가 **0**이다.
     (2026-09-22 M2 정정 — 원문의 총수 계수는 REQ-002가 요구하는 `favoritePlaces: [String: Place]` 선언까지 세어 AC-002 (3)의 **1**과 양립 불가했다. 실측: 총수 1 = 전부 favoritePlaces, `confirmedPlaces: [String: Place]` = 0. 본보기 `AddActivityView`도 같은 모양이다.)
  2. `confirmedPlace(_:)`의 본문이 `field(key).flatMap { $0.chosen == nil ? nil : confirmedPlaces[$0.id] }`
     형태다 — `$0.chosen == nil ? nil :` 절이 **있다**. 세는 명령:
     `grep -c "chosen == nil ? nil : confirmedPlaces" Shared/AddEventView.swift`가 **1**.
     **없으면 결함이 형태만 바꿔 살아 있다** — 신원 열쇠에서는 `chosen`을 지운 줄이 옛 좌표를
     계속 들고 있게 된다(`AddActivityView:493-494`가 본보기).
  3. 읽기 소비자 넷이 여전히 이 함수 하나를 통과한다 — `grep -n "confirmedPlace(" Shared/AddEventView.swift`가
     선언 1 + 호출 4(`:406`·`:444`·`:445`·`:516`·`:547`·`:548` 중 현행 여섯 자리)로, 사전을
     직접 조회하는 새 자리가 생기지 않았다. **자리가 늘었으면 계약 5 위반이다.**
  4. iOS·macOS 양쪽 컴파일 통과(AC-008 (2)(3)과 같은 실행에서 확인) — 타입이 바뀌므로 남은
     `String` 조회가 있으면 **컴파일이 잡는다.** 이 AC에서 컴파일이 실질적 검증인 유일한 절이다.

## AC-003 — 칩 탭 경로에 좌표 쓰기 자리가 정확히 하나 생겼다 ⬜

**관측자: 기계 (1)(2)(3) + 사람 (4).** (4)는 즐겨찾기 경로가 실제로 좌표를 싣는지이며 명령으로
잴 수 없다 — 이 카드에서 **가장 조용한 실패 모양**이다.

- **Given** `choose(field:value:)`(`:256`)가 `confirmedPlaces`에 한 번도 쓰지 않고
  (`grep -n "confirmedPlaces" Shared/AddEventView.swift`의 여덟 자리 중 그 함수 범위에 드는 것이
  0건), 즐겨찾기 칩이 동작하는 유일한 이유가 **`chosen`에 든 라벨이 곧 사전 열쇠이기 때문**이며
- **When** `choose`에 `place: Place? = nil`이 붙고 쓰기 한 줄
  `if c.fields[i].kind == .place { confirmedPlaces[field] = place ?? favoritePlaces[value] }`가
  들어가며 `choosePlace`(`:304-307`)가 그 자리를 거치게 되면
- **Then** 넷이 동시에 성립한다:
  1. `grep -c "confirmedPlaces\[field\] = place ?? favoritePlaces\[value\]" Shared/AddEventView.swift`가
     **1** — 쓰기가 한 자리다.
  2. `choosePlace`의 본문에 `confirmedPlaces[…] =` 대입이 **없다** — 자기 자리에서 쓰지 않고
     `place`를 실어 넘긴다. 세는 명령:
     `sed -n '/private func choosePlace/,/^    }$/p' Shared/AddEventView.swift | grep -c "confirmedPlaces\["`가 **0**.
  3. **순서가 `place ?? favoritePlaces[value]`다 — 뒤집혀 있지 않다.** 뒤집으면 검색해서 고른
     "스타벅스" 홍대점이 즐겨찾기 "스타벅스"의 좌표로 조용히 바뀐다. 코드 대조 항목이며 (1)의
     문자열 일치가 곧 이 판정이다.
  4. **시뮬레이터**: 일정 추가에서 출발지를 **즐겨찾기 칩**으로 고르면 이동시간이 계산되고 저장
     버튼이 열린다. **아무 일도 일어나지 않거나 이동시간이 비면 쓰기 자리를 안 만든 것이다** —
     열쇠만 바꾸고 이 절을 빠뜨리면 즐겨찾기로 고른 일정이 **좌표 없이** 저장되는데, 빌드도
     드라이버도 잡지 못한다.

## AC-006 — 앞 카드의 좌표가 뒤 카드에 붙지 않는다 ⬜

**관측자: 사람 전용.** 한 대화에 카드가 두 장 서야 하고, 그 사이 상태는 어떤 명령으로도 찍을 수
없다. `confirmedPlaces`가 비는 자리는 `resetConversation()`의 `:217` 하나뿐이므로
(`grep -n "confirmedPlaces = \[:\]" Shared/AIAssistant.swift`가 1건), 사전은 대화가 끝날 때까지 산다.

- **Given** 열쇠를 인자 슬롯으로 바꾸면(A안) 슬롯은 대화 내내 같은 문자열이라, **사용자가 이번
  카드에서 확정한 적 없는 이름**이 뒤 호출에 같은 슬롯으로 실려 와도 앞 카드의 좌표를 받는다
  (지금의 이름 열쇠에는 없던 경로다 — 이름이 다르면 안 걸렸다)
- **When** M1이 고른 안이 REQ-011을 만족하면
- **Then** **시뮬레이터에서 한 대화로 두 번 등록한다**:
  1. `내일 3시에 강남역 가야 해` → 되묻기 카드의 **출발지 줄**에서 `스타벅스`를 검색해 **홍대점**을
     고르고 등록.
  2. **같은 대화를 이어서** `모레 2시에 서울역 가야 해, 집에서 출발` → 등록.
  3. 만든 두 번째 일정을 시간표에서 탭 → **출발지가 '집'(또는 '집'으로 풀린 곳)이고, '스타벅스'가
     아니다.** '스타벅스'거나 홍대 좌표면 REQ-011 실패다 — 사용자가 이번에 말한 적 없는 곳에서
     출발하는 일정이 만들어진 것이고, 화면에 이름이 '집'으로 찍혀 있으면 알아챌 길이 없다.
  4. B안이 채택됐다면 이 경로는 **구조적으로** 막힌다(열쇠가 좌표를 구분한다). 그래도 실행해
     확인한다 — "막혔을 것"은 관측이 아니다.

  5. `Tools/GuardDriver.swift`의 변경 여부가 **인자 거동 변경 여부와 일치한다** — 거동이

     `git diff --stat <base>...HEAD -- Tools/GuardDriver.swift`와 M3의 변경 내용을 나란히 대조한다.
  6. **보이는 변화가 고른 안이 강제하는 것뿐이다**(REQ-022). A안이면 **0건**이고, B안이면 겹치는
     이름에 붙는 구분 문자열이 **세 표면**에 나타난다 — 확정 칩 · 확인 거품의 확정 요약 줄 · 칩
     재탭 시 검색창 씨앗(2026-09-22 M4 정정). 그 밖의 변화(배치·칩 문법·줄 구성·문구)는 0건이어야
     한다. 절 단위로 대조하고 **일괄 통과시키지 않는다.**

## AC-009 — 시뮬레이터 · 실기기 (대체 불가능한 증거) ⬜

**관측자: 사람 전용.** 이 카드가 고치는 값은 좌표이고 **좌표는 화면 어디에도 찍히지 않는다.**
그래서 아래 항목은 전부 "**어느 두 줄에 같은 상호의 다른 지점을 넣고, 그 결과로 무엇이 보여야
하는지**"를 문장 그대로 적는다. 관측 가능한 대리 신호는 셋이다 — **이동시간(0분인가)**,
**저장된 일정/활동 상세의 장소**, 그리고 **출발 알림 시각**.

**초기화 시점을 함께 적는다.** 아래는 설정 → "일정 모두 삭제"로 비운 직후 상태에서 시작한다.
즐겨찾기에 `집`이 하나 등록돼 있어야 한다(6·11번이 그 값을 쓴다).

### 시뮬레이터 (iPhone 17 Pro)

**`AddEventView` — 장소 줄 2 (REQ-001~004)**

1. "+" → 일정 추가. 출발지가 **현재 위치로 프리필**되고 칩 글자에 지명이 얹힌다(AC-004 (3)).
2. 목적지 줄에서 `서울역` 검색 → 고르기 → 이동 수단 줄에 **소요시간이 뜬다.** 안 뜨면 좌표가
   줄에 안 걸린 것이다.
3. 출발지 줄을 **즐겨찾기 `집` 칩**으로 다시 고르기 → 이동 수단 줄의 소요시간이 **다시 계산되고
   0분이 아니다.** 0분이거나 비면 REQ-003의 쓰기 자리를 안 만든 것이다(AC-003 (4)).
4. **핵심 — 이름 충돌.** 출발지 줄에서 `스타벅스`를 검색해 **강남점**을 고르고, 목적지 줄에서도
   `스타벅스`를 검색해 **홍대점**을 고른다(주소로 구분한다).
   → **이동 수단 줄의 소요시간이 0분이 아니다.** 0분이면 두 줄이 한 좌표로 무너진 것이고,
   이 카드가 닫으려는 바로 그 결함이다.
5. 저장 → 시간표의 이동 블록이 **0분 길이가 아니다.** 그 일정을 탭 → 출발지와 목적지가 **주소까지
   서로 다른 두 스타벅스**다.
6. 출발지를 `집`으로 바꾸고 목적지는 그대로 둔 채 저장 → 출발지가 즐겨찾기 `집`의 좌표로
   실린다(소요시간이 4번과 다르다).

**`AIAssistant` — 장소 줄 5 (REQ-010·012)**

7. 새 대화. `내일 3시에 스타벅스 가야 해, 스타벅스에서 출발할게` → 되묻기 카드에 **출발지 줄과
   목적지 줄이 함께** 선다. 출발지에서 `스타벅스` **홍대점**, 목적지에서 `스타벅스` **강남점**을
   고른다(주소로 구분).
   → **등록된다.** 지금은 두 줄이 한 좌표로 무너져 `isSamePlace`(`:1297`)가
   "출발지와 목적지가 '스타벅스'으로 같아요"로 **거절**한다 — 사용자가 두 지점을 분명히 골랐는데
   거절당하는 자리다. 수리 뒤에는 거절이 사라지고 일정이 만들어진다.
8. 만든 일정을 탭 → 출발지·목적지가 **주소까지 서로 다르다.** 이동시간이 0분이 아니다.
9. `내일 10시부터 12시까지 스타벅스에서 스터디, 스타벅스에서 출발해서 스타벅스로 돌아올게`
   → `create_activity` 카드에 **장소 줄이 셋** 선다(활동 장소 · 가는 편 출발지 · 오는 편 도착지).
   셋에 각각 **다른 지점**을 고른다(예: 강남점 · 홍대점 · 신촌점).
   → 시간표에 활동 블록과 **0분이 아닌** 이동 블록 둘이 함께 뜬다. 이 경로에는 `isSamePlace`
   가드가 없으므로(`:1613` 주석), 무너지면 **아무 신호 없이** 0분 구간과 활동 시작 시각 출발
   알림이 생긴다.
10. 9번에서 만든 활동을 탭 → 활동 장소가 **강남점**이고 이동 구간의 출발지가 **홍대점**이다.
11. **대화 범위(AC-006)**: 7번과 **같은 대화를 이어서** `모레 2시에 서울역 가야 해, 집에서 출발`
    → 등록 → 그 일정을 탭 → 출발지가 **`집`이고 '스타벅스'가 아니다.**
12. **구분 문자열 누출(REQ-012, B안일 때 특히)**: 7·9번에서 만든 일정·활동의 제목과 장소 이름에
    **구분용 문자열이 찍혀 있지 않다.** 도구 성공 문구와 마무리 문구에도 없다. 찍혀 있으면 내부
    문자열이 저장 데이터로 샌 것이다 — 같은 종류의 누출이 이 파일에서 **두 번** 있었다(`:44-48`
    주석). 단 **확인 직후 사용자 거품으로 바뀐 확정 요약 줄에는 구분 문자열이 있어야 한다**
    (REQ-022의 M4 정정 예외 — 칩과 같은 문자열을 찍는 자리). 거품에 이름만 찍혀 있으면 칩과
    거품이 다른 말을 하는 것이므로 그것이 결함이다.
13. **보임새 대조(REQ-022)**: 1~11을 훑으며 **고른 안이 강제하지 않는 변화가 하나도 없음**을
    확인한다. A안이면 변화 0건이고, B안이면 4·7·9번에서 겹치는 이름에 구분 문자열이 세 표면
    (칩 · 거품 확정 줄 · 재탭 검색창 씨앗)에 붙는 것뿐이다(12번·REQ-022의 2026-09-22 M4 정정).
14. 설정 → 텍스트 크기 최대 → 4·7·9번을 다시 본다. 칩이 잘리거나 줄이 겹치지 않는다
    (B안의 구분 문자열이 칩을 길게 만드는 유일한 자리다).

### 실기기 전용 (시뮬레이터로 대체 불가)

- **출발 알림이 실제로 온다** — 5·9번에서 만든 일정·활동의 출발 알림이 **도착/시작 시각이 아니라
  이동시간만큼 앞서서** 울린다. 0분 구간이 남아 있으면 알림이 시작 시각에 붙으므로, 이것이
  좌표 충돌의 **가장 손에 잡히는 증상**이다.
- 구글 캘린더 앱에서 5·9번의 블록이 **묶여** 보이고, 장소 필드에 구분 문자열이 없다(12번의 실기기 판).
- 칩 탭과 검색 결과 목록의 손맛 — 같은 이름의 후보 여럿을 주소로 골라내기가 실제로 되는지.
- VoiceOver로 4·9번의 장소 줄을 낭독 — 같은 이름의 두 줄이 소리로 구분되는지(B안이면 구분
  문자열이 낭독되고, A안이면 이름만 두 번 낭독된다 — **A안을 골랐다면 이것이 선언된 상실이다**).
