## 3. 오케스트레이터가 열어 둔 질문 (가)~(라)의 답 + 0.2.0 추가 (마)

### (가) 카드 재료가 수정·점심 줄을 받을 수 있는가 — 그대로는 아니다

- `placeRow(key:)` `:746-754`의 갈래는 `origin_query`·`place_query`·`travel_from_query`·`return_to_query`이고 **나머지는 `destinationField()`**(`:752`) — 키가 `"destination_query"`, 이름이 "목적지"인 줄이다.
- `parkForUnclearPlaces` `:918-958`은 `askFields(tool:args:)`(`:931`)로 줄을 만든 뒤 각 보류 키에 대해 `placeRow(key:)`를 부르고 **`item.key`로** 기존 줄을 찾아 바꾸거나 덧붙인다(`:942-943`). `clearedKeys`는 보류 키 집합이다(`:950`).
- `resolvePendingAsk`의 첫 주입은 `ask.fields`에서 **`kind == .place`이고 줄 키가 `clearedKeys`에 든 줄**만 본다(`:1238`). 줄 키가 `destination_query`이면 `new_place_query`·`lunch_place_query`는 비운 채로 남는다.
- 이 주입은 도구 이름을 보지 않는다(`:1222-1247`). 둘째 루프는 `askFields(tool:args:)`를 다시 구하는데(`:1249`), `askFields`의 `switch`에 `update_schedule` 갈래가 없어(`:501`·`:635` `default: break`) 수정 도구는 줄 0 — 아무것도 더하지 않는다. 반복 도구에서는 `lunch_place_query` 줄을 내지 않는다(`:535-559`). 그래서 첫 주입만 맞으면 확인은 성립한다.
- 맥락 줄: `filledValueLabels` `:886-910`은 `title` 키와 생성 세 도구의 장소 키만 본다 — 수정 도구(`title_query`)는 빈 배열.
- 생성 도구 이름 목록 둘(`pendingAsk(for:)` `:874` · J-1 후속 `:1308`)은 맥락 줄을 모을 때만 쓰인다. 보류 카드(`parkForUnclearPlaces`)는 그 목록을 지나지 않는다.
- `missingAskedArguments` `:1688-1695`는 `askFields`의 줄만 세므로 두 키의 영향을 받지 않는다. `executeUpdateSchedule`은 이 함수를 부르지 않는다.
- 결론: 줄 재료 두 갈래(`placeRow`) + 수정 맥락 줄(`filledValueLabels`) + 문구의 동사가 필요하다. `askFields`·`resolvePendingAsk`·`EditCardView`는 바꿀 필요가 없다(코드 읽기 — 실행 확인은 AC-005·AC-006).

### (나) 후보를 골라 확인하면 다시 묻지 않는가 — 묻지 않는다. 같은 이름 칩도 서로 덮지 않는다

- 후보 탭 → `choose(field:place:)` `:1063-1067` → `confirmedPlaceKey(for:in:)` `:1083-1092`가 열쇠를 정하고 `confirmedPlaces[key] = place`, 줄의 `chosen`도 같은 열쇠.
- 열쇠 사다리: 이름 → `이름 · 주소`(주소가 있을 때) → `이름 · 위도, 경도`(4자리). 열쇠가 이미 **다른 좌표**(50 m 밖, `isSamePlace` `:1088`)에 점유돼 있으면 다음 열쇠로 간다.
- 확인 → 보류 인자의 비운 키에 그 열쇠가 실림(`:1246`) → `runToolCalls`(`:1319`) → 실행부 → `adoptPlace(열쇠)` → `locallyResolvedPlace`(`:1362`, 공백만 다듬은 열쇠로 사전 조회)가 그 좌표로 푼다. 검색도 카드도 없다.
- 같은 이름 다른 좌표 둘을 한 카드의 두 줄에서 고르면 첫째는 `이름`, 둘째는 `이름 · 주소`(주소가 비면 `이름 · 좌표`) 열쇠가 된다 — 주소가 첫째와 같아도 `이름 · 주소` 열쇠는 아직 비어 있으므로 둘째가 그 열쇠를 쓴다(`:1084-1089`, 감사 1회차 A-9 정정) — 사전에서 서로를 덮지 않는다. **잠재 결함을 찾지 못했다**(코드 읽기). 회귀선으로 AI-20을 제안했다.
- 화면 쪽: 후보 칩은 `ForEach(places, id: \.self)`(`EditCardView.swift:349`)이고 `Place`는 네 필드 전체가 `Hashable`(`Models.swift:111-116`)이다 — 이름+좌표 키로 완전 중복을 지우면 같은 id가 남지 않는다. 칩에 주소 줄이 있어(`EditCardView.swift:365-367`) 같은 이름 지점을 화면에서 가를 수 있다. 다만 주소가 빈 결과는 이름만 보인다 — MapKit 폴백은 `placemark.title`이나 도로명 조각으로 주소를 채우고(`PlaceSearch.swift:125-129`) 모두 없으면 빈 문자열이 될 수 있으며, 카카오 결과의 주소 모양은 이 레인이 보지 못했다.
- 장소 줄에는 자유 텍스트를 확정하는 버튼이 없다(`EditCardView.swift:315-318` 주석, `placeSearchEditor`) — 사용자가 친 글자가 좌표 없이 실행부로 가서 다시 카드를 세우는 경로는 없다.
- 한계: 확정 사전의 열쇠는 **고른 장소의 이름**이다. 같은 대화에서 원래 질의('스타벅스 강남점')를 다시 말하면 사전에 없어 다시 묻는다 — 결함이 아니라 지금 계약이고, 운영자가 "이미 확정"으로 볼지는 `plan.md` §6에 질문으로 남겼다.

### (마) 조회 도구도 같은 카드·확인 경로를 지난다 — 결정 D-1 (b)의 코드 근거 (0.2.0)

## 6. 카드 본문·지시와 코드가 어긋난 자리

1. **AI-8은 반전할 것이 없다.** 카드는 "AI-2·AI-4·AI-5·AI-8 '확정' 기대가 '질문'으로 반전"이라 적었지만 AI-8의 기대는 이미 `unclear:스타벅스 대학로점`이다(`Tools/GuardDriver.swift:5013-5018`, 로그 `:562` ✓). R-5 정리만 한다.
2. **조회 경로 둘도 평탄화한다.** 카드 ③은 쓰기 둘(`:2813`·`:2250`)만 적었고, 같은 평탄화가 식사 추천(`:2703`)과 이동시간 조회(`:2762`·`:2765`)에도 있다 — 결정 D-1, 운영자가 (b) 조회도 카드로 확정했다(§3 (마)).
3. **순서는 카드가 정하지 않았다.** 카드는 중복 키(②)만 말하고 지금의 "낱말 만족 결과 먼저" 재정렬(`:3186-3187`)은 말하지 않는다. 원칙 문구("그대로")로 읽으면 제공자 순서다 — 결정 D-2. 오케스트레이터의 "두 함수가 죽는다"는 이 읽기(D-2 (a))를 전제로 할 때만 맞았고, 운영자가 D-2 (a)를 확정해 성립했다.
4. **점심은 위치를 옮겨야 한다.** 카드는 "같은 선택 카드"라고만 했지만, 지금 자리에서 카드를 세우면 확인이 통근 묶음을 한 벌 더 만든다(§4) — REQ-008·결정 D-4.
5. **수정 줄은 지금 재료로 서지 않는다.** "등록 경로는 새 카드 코드 없이 묻는다"는 맞지만, 쓰기 둘은 `placeRow` 기본 갈래 때문에 "목적지" 줄로 뜨고 고른 값이 주입되지 않는다(§3 (가)).
6. 줄번호 차이(사소): 카드의 재시도 블록 `:3098-3104`는 코드 줄이고, 블록 주석까지는 `:3094-3104`다.
