# SPEC-UIKIT-008 — acceptance.md

계획 SPEC이므로 전 AC를 ⬜(미확인)로 시작한다.

**이 문서의 조직 원리는 "누가 볼 수 있는가"다.** 이 카드가 고치는 것은 장소의 **좌표**와 카드의 **보임새**다. 좌표는 화면에 찍히지
않고, 보임새는 드라이버가 SwiftUI를 컴파일하지 않아 명령으로 볼 수 없다. 그래서 각 AC는 자기 판정이 **run/sync가 돌리는 명령**
(드라이버 · `grep` · 빌드 · `git diff`)으로 닫히는지, **시뮬레이터 앞의 사람만** 볼 수 있는지를 먼저 밝힌다. 둘이 섞인 AC는 절마다 갈라 적는다.

**드라이버가 볼 수 있는 것은 "도구 실행부와 카드 판정이 무엇을 돌려주는가"까지다.** 모델이 무엇을 보내는지, 카드가 화면에 어떻게
보이는지, 모델 루프가 카드 뒤에 무엇을 하는지는 AC-014·015만 본다. 241/241 초록인 후보 트리에 렌즈 결함이 있다는 사실이 이 구분의 이유다.

**재현 절의 이름.** run이 M1에서 더하는 드라이버 단언의 이름은 **두 자리** 번호 `AB-H01`~`AB-H11`로 시작하고 뒤에 공백이 온다(예:
`AB-H01 create_activity place_query`). 드라이버는 `"  ✓ \(label)"`·`"  ✗ \(label)"`로 찍으므로(`Tools/GuardDriver.swift:31-32`) `grep -c '✓ AB-H01'`은
`AB-H10`을 세지 않는다 — 한 자리 번호였다면 `AB-H1`이 `AB-H10`까지 셌다(감사 1회차 D6). 수용한 가설의 특성화 단언은 번호 뒤에 `[수용]`을, 경로가 없어진 가설의 특성화 단언은 `[경로 제거]`를 붙인다
(`AB-H09 [수용] …`·`AB-H03 [경로 제거] …` — spec REQ-001 극성 규칙). 이름을 바꾸면 AC의 명령을 같은 커밋에서 고친다.

**범위 명령은 커밋끼리 비교한다.** `git diff <커밋> HEAD`는 추적되지 않는 파일을 보지 않으므로 워크트리 루트의 `build-ios.log`·`build-mac.log`(이전 세션이
남긴 것, 커밋하지 않는다)는 어떤 AC에도 잡히지 않는다. `git status`를 판정에 쓰는 AC는 없다.

## AC-001 — 재현이 수리보다 먼저다 ⬜

**관측자: 기계.**

- **Given** `git diff --quiet e1a40a6 -- Shared/`가 exit 0인 트리(M1 시점)에서
- **When** run이 재현 단언 `AB-H01`~`AB-H11`(바라는 동작을 적는다)을 더한 드라이버를 `CLAUDE.md` 블록으로 컴파일해 돌리면
- **Then** 다섯이 동시에 성립한다:
  1. 로그에 `P/T 통과` 줄이 있다(컴파일 실패가 아니다). exit 1은 이 단계의 기대값이다.
  2. `progress.md` §E.2에 가설마다 (a) 단언 이름 (b) 후보 트리에서의 ✓/✗ 줄 원문 (c) 그 실행의 커밋 SHA가 적혀 있다.
  3. 재현 절 커밋이 드라이버만 바꿨다 — `git show --stat <M1 커밋>`의 소스 경로가 `Tools/GuardDriver.swift` 하나다.
  4. 후보에서 ✓로 나온(재현되지 않은) 가설마다 "재현 안 됨"이 적혀 있고, `git diff e1a40a6 HEAD -- Shared/AIAssistant.swift`에 그 가설을
     근거로 적은 헝크가 없으며, 그 단언은 바라는 동작 그대로 회귀 방지선으로 남아 있다(§E.2의 헝크 귀속 목록으로 대조).
  5. 바라는 동작이 아닌 단언은 둘뿐이다. **H-9**(해석 I-5로 수용) — M1에서 재현됐다면 §E.2에 M1의 ✗ 줄과 "재현됨 — 수용(I-5)"이 있고, 최종 단언 이름에 `[수용]`이 있으며 ✓로 찍힌다.
     **H-3**(D-5 (a)로 경로 제거) — M1에서 재현됐다면 §E.2에 M1의 ✗ 줄, "경로 제거(D-5 (a))", 경로를 없앤 코드 자리(후보 카드가 선 뒤 `runLoop`이 돌아오는 줄, 새 발화가 열린 카드를
     취소하는 `:285`)가 있고, 최종 단언 이름에 `[경로 제거]`가 있으며 ✓로 찍힌다. 세는 명령: `grep -c '✓ AB-H[0-9][0-9] \[수용\]' <최종 로그>`와
     `grep -c '✓ AB-H[0-9][0-9] \[경로 제거\]' <최종 로그>`가 각각 재현된 수(0 또는 1)와 같고, 다른 단언에는 두 표지가 없다.

## AC-002 — 채택 판정이 이름만 본다 ⬜

**관측자: 기계.**

- **Given** 최종 트리에서
- **When** 드라이버를 돌리면
- **Then** 셋이 동시에 성립한다:
  1. '강남' 단언에 주소 인자가 있다 — `grep -n 'drvTopMatches("강남"' Tools/GuardDriver.swift`가 찍는 모든 줄에 `address:`가 있다
     (후보 트리에서는 `:1835` 한 줄, 주소 없음). 주소 픽스처는 둘이다: `서울 강남구 선릉로100길 1` · `서울 강남구 삼성동 131`.
  2. 두 주소 모두 '강남' → '서울선릉과정릉'이 맞지 않는다(`AB-H04` ✓). 판정이 주소를 보지 않으므로 두 픽스처의 결과가 같다.
  3. 회귀 — '스타벅스 홍대점' → '스타벅스 대학로점'(`서울 종로구 대학로 116`)은 맞지 않고, → '스타벅스 홍대입구역점'(`서울 마포구 양화로 165`)은 맞으며,
     '홍대역' → '홍대입구역'은 맞다. AA-1 마지막 단언("테헤란로 152" → OO빌딩, 주소 `서울 강남구 테헤란로 152`)의 기대는 **맞지 않음(되묻기)**으로 바뀐다 — 이름만 보기 때문이다.
     그 교체를 뺀 1·더한 1로 §E.2에 적는다. `grep '✗' <드라이버 로그> | grep -c 'AA-1\|AB-H04'` = **0**.

## AC-003 — 후보 카드에서 고른 값이 열 조합 모두에서 실린다 ⬜

**관측자: 기계.** 좌표는 화면에 안 보이지만 드라이버는 레코드를 직접 읽는다.

- **Given** 즐겨찾기 `집`·`회사`가 있는 드라이버 상태에서 각 조합마다 후보 두 곳(첫째 = 틀린 지점, 둘째 = 맞는 지점)을 주입해 후보 카드를 열고
- **When** 둘째 후보를 `choose(field:place:)`로 고르고 확인(`drvResolvePendingAsk`)하면
- **Then** 만들어진 레코드의 해당 장소가 **둘째 후보의 이름과 좌표**다. 조합은 열 개다:
  1. `create_schedule` · `origin_query` 2. `create_schedule` · `destination_query` 3. `create_recurring_schedule` · `origin_query`
  4. `create_recurring_schedule` · `destination_query` 5. `create_activity` · `place_query`(이동 없음 — 수리 뒤에는 머무는 요청 카드의 출발지 줄에서 `이동 없음`을 고른 뒤) 6. `create_activity` · `travel_from_query`(왕복)
  7. `create_activity` · `travel_from_query`(편도) 8. `create_activity` · `return_to_query` 9. 한 호출의 두 키 동시 모호(`create_schedule`)
  10. 머무는 반복의 목적지 모호(`create_recurring_schedule`, 카드의 출발지 줄에서 `이동 없음`을 고른 뒤 목적지가 검색에 맡겨진다 — 레코드는 활동 블록뿐이고 그 장소가 둘째 후보다).
- 세는 명령: `grep -c '✓ AB-H01' <로그>` ≥ **10** 이고 `grep '✗' <로그> | grep -c 'AB-H01'` = **0**. 후보 트리에서의 예측은 4·5·7·8번의 실패다(AC-001 기록). 10번은 `이동 없음` 선택지가 수리로 생기므로 M1 재현 대상이 아니고, 수리 커밋에서 회귀 방지선으로 더한다.
- 성공 문구가 나오는데 장소가 비거나 첫째 후보인 레코드가 하나라도 있으면 FAIL이다 — 조용한 실패의 모양이다.
- REQ-010 뒤에는 머무는 반복이 출발지 선택을 거쳐서만 실행부에 닿으므로 두 키가 같은 모호한 질의로 실행부에 오는 상태는 카드로 닿지 않는다. 드라이버의 직접 호출로만 닿는
  그 상태의 결과는 이 AC의 대상이 아니다(잔여 위험 — `plan.md` §3).
- 열 조합의 기대는 E5 재결정 (나)(0.1.8)로 바뀌지 않는다 — 5·10번은 출발지 줄에서 `이동 없음`을 고른 뒤라 50 m 판정에 닿지 않는다. 다만 후보 카드에서 고른 장소는 이 대화의 확정 장소가 되므로,
  뒤이은 머무는 요청에서 그 장소가 앵커이면 앱이 좌표를 아는 앵커로 REQ-010의 50 m 절에 든다(AC-008 (11)의 `AD-E5`가 이 모양을 확정 사전 시드로 잰다).

## AC-004 — 다중 호출이 사라지지 않고, 한 요청이 두 건이 되지 않는다 ⬜

**관측자: 기계 (1) + 기계·코드 대조·사람 (2).**

- **Given** 후보 카드 하나가 열린 상태에서
- **When** 같은 턴에 다른 입력의 모호한 등록 호출이 한 번 더 오면(`drvPark`를 서로 다른 입력으로 두 번)
- **Then**:
  1. 둘째 호출의 도구 결과가 "자동으로 진행"을 말하지 않고, 등록하지 않았으며 카드가 끝난 뒤 다시 호출하라고 말한다. 카드는 한 장이다. `store.events`에 둘째 호출의 레코드가 없다(`AB-H02`).
  2. 같은 요청이 두 건이 되지 않는다 — 코드 대조: 도구 실행 중 후보 카드가 섰으면 `runLoop`이 그 턴에서 모델을 다시 부르지 않고 돌아오는 자리를 `progress.md` §E.2에
     함수·줄번호로 적는다. 드라이버: `AB-H03`은 M1에서 재현되면 `[경로 제거]` 특성화 단언으로 바뀐다(AC-001 (5)). 사람: AC-014 1번에서 카드 아래에 모델 말풍선이 붙지 않는다.
     D-5 (a)의 전제가 run의 착수 전 확인에서 깨지면 run은 블로커를 돌려주고, 이 절은 리드가 다시 정한 결정으로 개정될 때까지 판정하지 않는다.
- 후보 트리에서의 예측: (1) "자동으로 진행돼요" 문구 · (2) 2건(AC-001 기록 H-2·H-3).

## AC-005 — 후보가 보이고, 카드가 정해진 값을 적는다 ⬜

**관측자: 기계 (1)(2)(3)(5) + 사람 (4).**

- **Then** 다섯이 동시에 성립한다:
  1. 후보 카드의 모든 후보 줄이 `startsOpen == true`다(드라이버 `AB-H05`). `grep -c 'AI 카드는 전부 기본값 false' Shared/EditCard.swift` = **0**(후보 트리 1).
  2. 맥락 줄 — `create_schedule`·`create_activity`·`create_recurring_schedule` 각각에 대해, 실행 전 카드(`drvAsk`)와 후보 카드(`drvPark`) 모두의
     `stated`에 제목과 **카드가 묻지 않는 모델 채움 장소 값**이 들어 있다(드라이버 6단언 이상). 후보 트리에서는 활동·반복 후보 카드의 `stated`가 빈 배열이다(H-6).
  3. 맥락 줄을 만드는 함수가 하나다 — 그 줄을 만드는 선언이 `Shared/AIAssistant.swift`에 한 건이고, `grep -c 'guard tool == "create_schedule"' Shared/AIAssistant.swift`가
     후보 트리의 **1**보다 줄었거나, 남았다면 그 줄이 맥락 줄과 무관한 자리임을 §E.2에 적는다.
  4. **사람**: AC-014 1·3·4번에서 후보가 **첫 화면에** 보이고, 카드 위쪽 "말씀하신 대로"에 제목이 보인다.
  5. 후보 캡션에 구현 용어가 없다 — `grep -c '첫 검색 결과가 말씀하신' Shared/AIAssistant.swift` = **0**(후보 트리 1). 채택 원문(`plan.md` §2 D-10 표)이 있다 —
     `grep -c '검색 결과가 말씀하신 지점인지 확실하지 않아요' Shared/AIAssistant.swift` ≥ **1**, `grep -c '아래 후보에서 맞는 곳을 골라 주세요' Shared/AIAssistant.swift` = **1**.

## AC-006 — 같은 이름 줄에 양성·음성 대조가 있다 ⬜

**관측자: 기계.**

- **Then** 다섯이 동시에 성립한다(드라이버, (4)는 `grep`):
  1. 음성 대조(규칙이 발동해야 하는 쪽) — `create_schedule` 출발지·목적지가 모두 `스타벅스` → 두 줄 모두 캡션과 함께 선다. `create_activity` 세 키가 모두 `스타벅스` → 세 줄.
  2. **양성 대조(규칙이 발동하지 않아야 하는 쪽)** — 출발지·목적지가 **같은 즐겨찾기 이름** `집`/`집` → 같은 이름 줄이 서지 않는다. 후보 트리의 AA-2(`GuardDriver.swift:1856-1863`)는

    "'집'에서 출발하는지 한 번 더 골라 주세요. 가는 이동이 필요 없으면 '가는 편 없음'을 고르면 돼요."다.
    → '가는 편 없음'을 골라 "등록하기" → 활동 1건 + 오는 편 이동 1건만 생긴다. 활동 블록의 장소가 비어 있지 않다. 활동 장소에 후보 카드가 먼저 떴다면 고른 장소가 실렸는지 적는다.
    전사에서 모델이 보낸 `travel_from_query` 값을 적는다.

### 파트 D — 머무는 요청 (D-8 운영자 문구 · 해석 확인)

12. `매주 월수금 12시부터 13시까지 집에서 점심식사`
    → **기대:** 카드에 "출발지" 줄과 "반복 기간" 줄이 있고, 이동수단·도착 여유·알림 줄은 **없다**. 출발지 줄의 캡션은 "'집'에서 출발하는지 골라 주세요. 이동이 필요 없으면 '이동 없음'을
    고르면 돼요."(I-6)이고, 칩은 집·회사·현재 위치·이동 없음·장소 검색이며 **어느 것도 미리 선택돼 있지 않다**(I-2). "말씀하신 대로"에 이동이 없다고 정해 적혀 있지 않다.
    → '이동 없음'과 `4주`를 골라 "등록하기" → 결과 문구가 "한 장소 반복 활동 12건(12:00~13:00, 장소 '집')"과 "이동 구간은 만들지 않았어요"를 말한다. 시간표에 활동 블록만 있고
    이동 블록이 없다. 출발지 줄이 없거나 이동수단 줄이 떴다면 모델이 출발지를 다른 값으로 보낸 것이다 — 전사의 `origin_query` 값을 적는다.
13. (12번과 **같은 대화**) `방금 만든 반복 일정 이동수단을 자동차로 바꿔줘`
    → **기대:** "이미 삭제됐을 수 있어요"가 **나오지 않는다.** 이동 구간이 없어 바꿀 것이 없다는 사실 문구가 나온다. 나온 문구를 그대로 적는다. 끝나면 블록을 열어 "반복 일정 전체 삭제".
14. (새 대화) `매주 월수금 12시부터 13시까지 집에서 점심식사`
    → 12번과 같은 카드가 뜨면 출발지로 ⭐ `회사`, `4주`를 골라 "등록하기"
    → **기대:** 곧바로 등록되지 않고 이동수단·도착 여유·알림을 묻는다(두 번째 카드 또는 모델의 질문 — I-1). `대중교통`·`10분`·`10분 전 알림`으로 답한다
    → 회사→집 가는 구간(12:00 도착)·집→회사 오는 구간(13:00 출발)·집의 활동 블록(12:00~13:00)이 각각 12건 생긴다(통근 경로 — B-1). **볼 것:** '반복 기간'을 다시 묻는지(H-9와 같은 모양 — 적기만 한다), 등록 결과에 활동 블록 12건이 있는지(없고 가는 구간만 있으면 재호출이 끝 시각을 빠뜨린 것 — 잔여 위험, 전사의 `return_time`을 적는다).
    → 끝나면 아무 블록이나 열어 "반복 일정 전체 삭제".
15. (새 대화) `매주 화목 12시에 집에서 점심식사`(끝 시각 없음)
    → **기대:** 카드가 뜨기 전에 어시스턴트가 끝나는 시각을 **묻는다**(I-4 운영자 문구 · B-2·B-3). 스스로 채워 재호출하지 않는다(전사로 확인). `13시`로 답한다
    → 카드(출발지·반복 기간)가 뜬다. '이동 없음'과 `4주`를 골라 "등록하기" → 12:00~13:00 활동 블록만 생기고 이동 블록이 없다.
    **볼 것:** 끝 시각을 묻기 전에 카드가 먼저 떴는지, 등록 뒤 "반복 기간"을 다시 묻는지(H-9 — 해석 I-5, 기록이 통과 조건이다). 끝나면 블록을 열어 "반복 일정 전체 삭제".
16. (새 대화) `내일 12시부터 13시까지 집에서 점심식사`
    → **기대:** 카드에 "가는 편 출발지" 줄 하나가 있고(칩 집·회사·현재 위치·이동 없음·장소 검색, 미리 선택 없음) 이동수단·도착 여유·알림 줄은 **없다**(T-1). 전사에서 모델이 보낸
    `travel_from_query` 값을 적는다 — `집`이면 줄 캡션이 "'집'에서 출발하는지 골라 주세요. 이동이 필요 없으면 '이동 없음'을 고르면 돼요."다.
    → ⭐ `회사`를 골라 "등록하기" → 곧바로 등록되지 않고 이동수단·도착 여유·알림을 묻는다(I-1). `대중교통`·`10분`·`10분 전 알림`으로 답한다 → 집의 활동 1건(12:00~13:00)과
    회사→집 가는 이동 1건(12:00 도착)이 생긴다. 집→회사 오는 이동은 **생기지 않는다**(경계 B-1 — 생겼다면 적는다).

**16a.** (새 대화, 16번에 이어 초기화 없이) `내일 오후 3시부터 4시까지 스타벅스 홍대점에서 공부`
    → **기대:** 카드에 "가는 편 출발지" 줄 하나가 있고(칩 집·회사·현재 위치·이동 없음·장소 검색, 미리 선택 없음) 이동수단·도착 여유·알림 줄은 **없다**(T-1). `현재 위치`를 골라 "등록하기"
    → **활동만 등록되지 않고** 이동수단·도착 여유·알림을 묻는다(두 번째 카드 또는 모델의 질문 — I-1). 검색으로만 풀리는 장소는 앱이 좌표를 몰라 50 m로 판정하지 않기 때문이다(REQ-010 0.1.8, E5 (나)).
    위치 권한 요청이 뜨면 허용하든 거절하든 기대는 같다. 묻는 것을 확인하면 답하지 않고 ↺(새 대화)로 버린다. **볼 것:** 시간표에 15:00~16:00 활동 블록이 생겼으면 적는다(생기면 결함이다).
    전사에서 모델이 보낸 `travel_from_query` 값을 적는다.

### 파트 E — U-2 네 화면
