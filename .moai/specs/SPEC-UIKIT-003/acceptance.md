# SPEC-UIKIT-003 — acceptance.md

계획 SPEC이므로 전 AC를 ⬜(미확인)로 시작한다.

본 SPEC은 **전환**이다 — 바뀌는 것은 의도한 것뿐이고, 의도하지 않은 것은 하나도 안 바뀜을 보인다.
그래서 어포던스 대조(AC-007)가 문서의 중심이고 **절 단위를 일괄 통과시키는 경로가 없다.**

카드 렌더링·제스처·접근성 낭독은 가드 밖이다(드라이버는 SwiftUI 뷰를 컴파일 대상으로 삼지
않는다). **AC-010(시뮬레이터·실기기)이 대체 불가능한 증거**이며 "드라이버 초록"으로 갈음하지
않는다 — 205/205 초록 다음 날 실기기 결함 7건이 나온 이력이 있다.

본 SPEC은 공유 컴포넌트를 고치므로 **안 건드린 두 화면(AI 카드·`AddEventView`)이 의도대로 함께
바뀌었는지**도 증거다(AC-002). "무변경"이 아니라 "의도한 변경만"이 통과 기준인 유일한 자리다.

## AC-001 — 기준 없는 시각 줄이 네 경로 전부에서 성립한다 ⬜

- **Given** `.datetime` 줄을 만드는 곳이 `AddEventView.swift:218`과 `AIAssistant.swift:590`
  **2곳뿐**이고 둘 다 기준이 있는 줄이며(실측), `EditField`에 `anchored`가 없고
- **When** `var anchored: Bool = true`가 기본값과 함께 추가되고 해석·매핑·글자·확정 네 경로가
  갈라지면
- **Then** 여섯이 동시에 성립한다:
  1. `grep -c "kind: .datetime" Shared/AddEventView.swift Shared/AIAssistant.swift`의 합이
     여전히 **2**(각 1)이고, 그 두 줄에 `anchored:`가 **없다** — 기본값이 있으므로 기존 생성부가
     바뀔 이유가 없다. 전환으로 새로 생기는 활동의 시각 줄은 다른 파일에 있으므로 이 계수에
     들지 않는다.
  2. `git diff origin/master...HEAD -- Shared/AIAssistant.swift Shared/AddEventView.swift`가
     **빈 diff**다(REQ-041).
  3. `BesirTime.parseDatetime`의 접두 목록에서 **빈 문자열이 마지막**이다 — 앞에 있으면
     `hasPrefix("")`가 항상 참이라 `arr:`가 영영 도달하지 않는다. 코드 대조 항목이다.
  4. `grep -c '"arr:" ?' Shared/EditCard.swift`가 **0** — `customLabel`의 삼항이 사라지고
     `BesirTime.anchor(ofPrefix:)` 경유가 됐다(계약 5).
  5. `BesirTime.anchor(ofPrefix:)`의 본문이 **무변경**이다 — `default: return nil`이 이미 `""`를
     "기준 없음"으로 답하므로 고칠 이유가 없다. 고쳐져 있으면 필요 없는 변경이다.
  6. **시뮬레이터**: 활동 추가에서 시작 시각을 고르고 확인을 누르면 칩이 확정 상태(체크 + 굵게)가
     된다. **조용히 아무 일도 일어나지 않으면 (d)의 확정 경로를 안 가른 것이다** — 이 카드에서
     가장 조용한 실패 모양이라 빌드도 드라이버도 잡지 못한다.

## AC-002 — 시각 줄 배치가 세 화면에서 같이 바뀐다 ⬜

- **Given** `datetimeRow`(`EditCardView.swift:181-203`)가 기준 칩 둘과 시각 칩 하나를 **한**
  `ChipFlow`에 두어 폭에 따라 줄바꿈 위치가 달라지고, 순서가
  `ForEach([ScheduleAnchor.arrival, .departure])`(`:184`)라 도착 기준이 먼저이며
- **When** 기준 칩 한 줄 + 아래 시각 칩 한 줄로 나뉘고 순서가 `[.departure, .arrival]`이 되면
- **Then**
  1. `grep -c "ScheduleAnchor.arrival, .departure" Shared/EditCardView.swift`가 **0**이고
     `.departure, .arrival`이 **1** — 순서가 실제로 뒤집혔다.
  2. `datetimeRow` 안에 `ChipFlow`가 **둘**이다(또는 기준 칩 줄과 시각 칩 줄이 별도 컨테이너다) —
     하나로 남아 있으면 배치가 여전히 폭의 함수다.
  3. **시뮬레이터 — 세 화면 전부**: (i) 이동 일정 추가 폼, (ii) AI 채팅의 되묻기 카드,
     (iii) 활동 추가. (i)·(ii)에서 **출발 기준 → 도착 기준** 순으로 한 줄, 그 아래 줄에 시각 칩.
     (iii)에서는 기준 칩 줄이 **통째로 없고** 시각 칩만 있다.
  4. 접근성 텍스트 최대 크기에서도 기준 칩 둘이 한 줄이고 시각 칩이 그 아래다 — 감겨서
     시각 칩이 기준 칩 옆으로 올라오지 않는다.
  5. `AddEventView`·`AIChatView`·`AIAssistant`는 **한 줄도 바뀌지 않았다**(AC-001 (2)) — 이 변경은
     공유 컴포넌트 안에서만 일어난다. 두 화면에 손을 댔다면 REQ-041 위반이다.

## AC-003 — 흐림 판정이 자기가 속한 줄을 본다 ⬜

- **Given** `departureAnchored`(`EditCardView.swift:74-77`)가
  `card.fields.first(where: { $0.kind == .datetime })` 한 줄로 카드 전체의 여유 줄 흐림(`:142`·
  `:149`)을 정하고, 활동 카드는 시각 줄을 **둘** 든다
- **When** 판정이 `kind == .datetime && $0.anchored`를 보게 되면
- **Then**
  1. `grep -c "kind == .datetime })" Shared/EditCardView.swift`가 **0** — 기준 조건 없는
     `first(where:)`가 남아 있지 않다.
  2. 기존 화면(`AddEventView`)의 흐림 동작이 **그대로**다 — 시각 줄이 하나뿐인 카드에서는 두 식이
     같은 줄을 고른다. 시뮬레이터에서 출발 기준을 고르면 도착 여유 줄이 흐려지고
     "출발 기준이라 쓰지 않아요"가 붙는다(`:143`).
  3. **시뮬레이터 — 이 AC는 관측 가능한 결함을 막는다**(D-3 해소로 활성). 활동 추가에서 "가는
     이동"을 켜고 시작 시각을 확정한다 → **"가는 편 도착 여유" 줄이 흐려지지 않고 캡션도 붙지
     않는다.** 흐려지면 REQ-003을 안 했거나 REQ-014를 먼저 한 것이다(원인은 두 화면이 아니라
     `currentBasis`의 `?? .departure` 폴백이므로, 화면만 들여다보면 찾지 못한다).
  4. 활동 카드에는 기준 있는 시각 줄이 **하나도 없으므로** 고친 뒤 `first(where:)`가 nil을
     돌려주고 `guard … else { return false }`가 걸린다 — 가는 편은 도착 기준 구간이라 여유를
     실제로 쓰므로 "안 흐려짐"이 맞는 결과다. 코드 대조 항목이다.
  5. `?? .departure` 폴백(`EditCardView.swift:168`)이 **무변경**이다 — 기준 있는 줄에서는 옳은
     방어이고, 고치면 기존 두 화면의 동작이 함께 바뀐다. 고쳐져 있으면 범위를 넘은 것이다.

## AC-004 — `AddActivityView`의 값이 카드 하나에 산다 ⬜

- **Given** 폼 값이 `@State` **12개**(`AddActivityView.swift:14-29`)에 흩어져 있고 제출 판정이
  별도 계산 프로퍼티 `canSave`(`:35-41`)이며, 다리 켜기/끄기가 조건부 섹션(`:100`·`:108`)이고
- **When** 전환이 끝나면
- **Then**
  1. `grep -c "@State" Shared/AddActivityView.swift`가 **줄어들고**, 남은 것은 카드가 가질 수
     없는 것뿐이다(카드, 좌표 사전, 진행 깃발, 줄이 빠져 있는 동안의 기억값). 남은 항목을
     **하나씩 이름과 이유로 적는다** — "줄었다"로 일괄 통과하지 않는다.
  2. `grep -c "canSave" Shared/AddActivityView.swift`가 **0**이고 제출 판정이 `card.isReady`다.
  3. 다리 줄이 **배열 멤버십**으로 들고 난다 — `outbound_enabled`가 꺼진 상태에서
     `card.fields`에 `origin_query`·`outbound_mode`가 **없다**. 조건부 뷰(`if`)로 숨기는 형태가
     아니다(숨긴 줄은 `isReady`에 계속 걸린다).
  4. 토글을 껐다 켜면 방금 고른 출발지가 **되살아난다** — 되심지 않으면 값을 잃는다.
  5. 장소가 없을 때 다리 줄 자체가 생기지 않고, "장소를 정하면 이동도 함께 만들 수 있어요"가
     **장소 줄의 `note`**로 내려가 있다 — 없는 줄을 설명하는 독립 문구가 남아 있지 않다.

## AC-005 — 여유·알림이 줄이 되고, 카드 신원이 흔들리지 않는다 ⬜

- **Given** `defaultNotify = 30`(`:33`)과 `defaultBuffer = 10`(`:32`)이 상수이고 화면이 둘 다
  묻지 않으며, 캡션이 "여유 10분 · 알림 30분 전"(`:116`)으로 둘을 나란히 보여주고
- **When** `notify_lead_minutes`(요청 ②)와 `buffer_minutes`(D-3) 줄이 동적 멤버십으로 들어오면
- **Then**
  1. `grep -c "defaultNotify\|defaultBuffer" Shared/AddActivityView.swift`가 **0**.
  2. 알림 옵션이 `AddEventView.notifyLeadRow`(`:246-252`)와 **같은 넷**(출발 시각·10분 전·30분 전·
     1시간 전), 여유 옵션이 `AddEventView`의 여유 줄(`:223-226`)과 **같은 넷**(0·10·20·30분),
     둘 다 직접입력 허용이다 — 두 폼이 다른 보기를 내면 같은 값을 두 문법으로 배운다.
  3. 캡션이 **통째로 사라졌다** — 두 값이 모두 줄이 되어 남길 것이 없다. 캡션이 남아 있으면
     줄과 캡션이 어긋날 자리를 그대로 둔 것이다.
  4. **여유 줄의 이름이 "가는 편 도착 여유"다** — `AddEventView`의 "도착 여유"와 다른 유일한
     자리이고, 다른 이유가 `Store.swift:238`(복귀 구간 버퍼 `0` 고정)에 있다. 이름에서 "가는
     편"이 빠져 있으면 줄이 오는 편에도 적용된다고 거짓말하는 것이다.
  5. 여유 줄이 `outbound_enabled`와 함께 들고 난다 — 가는 이동을 끄면 여유 줄도 **사라진다**
     (오는 편만 만드는 경우 적용될 데가 없다).
  6. `Store.addActivityWithTravel` 호출의 `notifyLeadMinutes:`·`bufferMinutes:`에 **카드가 고른
     값**이 실리고, 복귀 구간의 `bufferMinutes: 0`은 **그대로다**. `Shared/Store.swift`는
     **한 줄도 바뀌지 않는다**(값이 없던 게 아니라 화면이 묻지 않았다).
  7. 카드는 `.task`에서 **한 번** 만들어진다 — `EditCardView`가 계산 프로퍼티·`Group`·`AnyView`·
     가변 `.id`로 감싸여 있지 않다. **시뮬레이터**: 장소 검색창에 두 글자 이상 연속으로 쳐도
     글자가 지워지거나 에디터가 닫히지 않는다(카드가 매 렌더 새로 생기면 한 글자도 못 친다).
  8. 화면 header·footer가 남아 있고 `EditCardChrome(header: nil, confirmTitle: nil)`로 카드 쪽
     크롬이 꺼져 있다 — 제목이 둘, 제출 버튼이 둘로 보이지 않는다.

## AC-007 — 어포던스 36절 개별 대조 ⬜

**일괄 통과 경로가 없다.** 아래 36절을 하나씩 ✅/⚠️/❌로 적고, 형태가 바뀐 절은 바뀐 형태를
함께 적는다. 세는 명령 — 번호가 1..36으로 빠짐없이 이어지는지 본다:

```bash
sed -n '/^`AddActivityView` (22절)/,/^\*\*형태가 바뀌는/p' acceptance.md \
  | grep -oE '(^|· )[0-9]+ ' | grep -oE '[0-9]+' | sort -n | uniq | wc -l   # → 34
```

(줄머리의 `1`·`23`은 앞 접두사에 붙어 잡히지 않으므로 **34 + 2 = 36**이다. 34가 아니면 번호가
겹치거나 빠진 것이다.)

## AC-008 — 접근성 계약이 순증이고, 잃는 것이 적혀 있다 ⬜

- **Given** 두 화면의 접근성 호출과 `@ScaledMetric`이 각각 **0건**이고
  (`grep -c "accessibility\|ScaledMetric" Shared/AddActivityView.swift Shared/ActivityDetailView.swift`)
- **When** 전환이 끝나면
- **Then**
  1. 컴포넌트가 가진 것이 두 화면에 전부 들어온다: 줄 단위 그룹 낭독 · 선택 상태 3중 표현(색 +
     체크 글리프 + 굵기) · `.isSelected` 특성 · 칩 높이 iOS 44 / macOS 28의 `@ScaledMetric`.
  2. **잃는 것을 숨기지 않는다** — 세그먼트 `Picker`의 "조정 가능" 특성과 좌우 스와이프 선택,
     `Toggle` 넷의 스위치 특성, `Form`의 섹션 헤더 랜드마크 낭독. 이 넷을 acceptance 본문에
     적은 채로 통과한다(적지 않고 통과하면 후퇴를 숨긴 것이다).
  3. **시뮬레이터 + VoiceOver**: 활동 추가의 각 줄이 "줄 이름 + 고른 값"으로 이어 읽히고,
     이름 없는 버튼이 하나도 없다.

## AC-010 — 시뮬레이터·실기기 (대체 불가능한 증거) ⬜

**초기화 시점을 함께 적는다.** 아래는 설정 → "일정 모두 삭제"로 비운 직후 상태에서 시작한다.

**시뮬레이터 (iPhone 17 Pro)** — 입력 문구와 기대 결과:

1. "+" → 활동 추가. 제목에 `스터디 모임` 입력 → 제목 칩이 확정된다.
2. 장소 줄에서 `강남역` 검색 → 결과에서 고르기 → 이름과 주소가 확정 칩으로 남는다.
3. 시작 줄 → 시각 칩 탭 → 내일 오후 2시 선택 → **확인** → 칩이 체크 + 굵게로 바뀐다.
   **기준 칩 줄이 없다.**
4. 종료 줄 → 오늘 오전 9시(= 시작보다 앞) 선택 → 확인 → **거절 표시가 뜨고 확정되지 않는다.**
   줄 `note`에 왜인지 적혀 있다. 이어서 내일 오후 4시 선택 → 확정된다.
5. "가는 이동" 켜기 → 출발지·이동수단·**"가는 편 도착 여유"** 줄이 나타난다. 출발지 `서울역`
   고르기, 지하철 고르기.
6. **여유 줄이 흐려져 있지 않다** — 시작 시각을 이미 확정한 상태(3번)인데도 정상 색이고
   "출발 기준이라 쓰지 않아요"가 붙어 있지 않다. 흐려져 있으면 REQ-003 실패다(AC-003 (3)).
   `20분` 고르기 → 확정된다.
7. "이동 알림 받기"가 켜진 상태에서 **알림 줄이 보인다** → `1시간 전` 고르기. 끄면 알림 줄이
   **사라지고**, 다시 켜면 `1시간 전`이 **되살아난다**.
8. **캡션 "여유 10분 · 알림 30분 전"이 화면 어디에도 없다** — 두 값이 줄이 됐으므로.
9. "가는 이동" 끄기 → 출발지·이동수단·여유 줄이 사라진다. 다시 켜면 `서울역`·지하철·`20분`이
   되살아난다.
10. 추가 → 시간표에 활동 블록과 이동 블록이 함께 뜬다. 이동 블록 상세의 도착 여유가 **20분**이다
    (6번에서 고른 값이 실제로 실렸는지 — 상수 10분이면 REQ-014 실패다).
11. 만든 활동을 탭 → 상세가 **`Form`이 아니라 다른 세 화면과 같은 카드 문법**으로 열린다.
12. 상세에서 장소를 `홍대입구역`으로 다시 고르고 저장 → 주변 맛집 "추천 보기"가 **홍대 주변**을
    보여준다(강남 주변이 남아 있으면 ❌).
13. 이동 일정 추가 폼을 열어 시각 줄 확인 → **출발 기준 → 도착 기준** 한 줄, 그 아래 시각 칩.
    이어서 출발 기준을 고르면 그 폼의 도착 여유 줄이 **흐려진다** — 기존 동작은 그대로다
    (AC-003 (2)). 활동 쪽이 안 흐려지는 것과 나란히 확인해야 REQ-003이 "판정 대상을 바꿨을 뿐
    끄지 않았다"는 것이 보인다.
14. AI 채팅에 `내일 3시에 강남역 가야 해` → 되묻기 카드의 시각 줄도 같은 배치다.
15. 설정 → 텍스트 크기 최대 → 1·3·13을 다시 본다. 칩이 잘리거나 시각 칩이 기준 칩 옆으로
    올라오지 않는다.

**실기기 전용** (시뮬레이터로 대체 불가):

- 출발 알림이 실제로 **온다**(활동에 붙은 이동 구간의 리드 시간이 고른 값 그대로인지).
- 칩 탭과 날짜 바퀴의 손맛 — 칩 높이 44pt가 손가락에 맞는지.
- 구글 캘린더 앱에서 활동 블록과 이동 블록이 **묶여** 보이는지.
- VoiceOver 낭독(AC-008 (3))을 실제 음성으로.
